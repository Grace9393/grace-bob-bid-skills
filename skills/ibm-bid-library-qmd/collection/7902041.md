We designed and built a set of REST APIs for the Home Office in 2017-21 as a key part of the National Law Enforcement Data Programme (NLEDP), to replace the Police National Computer with a modern, cloud-native, API-based data platform.

We established an API strategy drawing on best-practice including Government Digital Service and wider industry API standards, and the Richardson Maturity Model (RMM). We designed the catalogue of APIs to expose policing data interactions as a set of REST resources/routes. We aligned our design with the Home Office POLE domain model and modelled APIs on the 4 major resources - person, object, location and event.

The POLE resources contained sub-resources to support the range of interactions required. For example, Person contained sub-resources to allow only certain parts of a subject’s data to be retrieved e.g. characteristics, identity numbers and warning markers. Similarly, Event sub-resources represented policing nouns such as arrests, offences and intelligence reports. The routes/URL structure was formed from these resources and sub-resources, making it easy for consuming applications from the 40+ Police Forces and other Agencies to use NLEDP APIs.

Multiple verbs were supported for access to the routes/resources, following RMM level 2 to align with HTTP standards. This used GET for retrieval, POST and PUT to create and update resources and DELETE to remove. The requirements needed partial update support, especially for system-to-system interactions, where only a small number of attributes were supplied in the request and updated to the resource. The PATCH verb was used for these partial updates, whereas PUT entirely replaced a resource.

We implemented content negotiation to allow versioning of APIs to allow breaking changes to be accessed using a new version number. The version number is expressed as an HTTP header, using content negotiation to determine the correct version of the resource to return.
