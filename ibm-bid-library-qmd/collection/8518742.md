The IaaS Provider runs the common C2 system. We’ll support them, supplying the common language data structures for cross-platform autonomous behaviours, using open standards to create them, accessible through OpenAPIs, enabling a high degree of re-use.
 
Before different RAS can execute a mission such as Sense-shoot, or overwatch, each type must be integrated onto the C2 system supported by its specific data structures for the platform, payload, and mission data. Once each is completed, we’ll work with the IaaS Provider, incrementally combining data structures to enable platforms to coordinate and cross-communicate.
 
We’ll run Design Thinking workshops with all partners to understand the missions, expecting each will require different mixes of platform, payload, and mission data. We will lab-test our data structures can persist and transmit the data required by the missions and assess data volumes and the impact they will have on current storage; being cloud-based, we’re in control of how the data is stored/persisted.
 
We will create good documentation (using Swagger) to minimise the partners’ effort in mapping the data structures for each RAS. Addressing the integration backlog with any spare capacity will enable us to get ahead of demand. We will update the partners and ecosystem regularly.
 
The ecosystem will help us understand the value of the data structures and APIs we’re developing. We’ll be mindful of extant standards and will engage the standards bodies through IBM’s established network to determine the value if of sharing with them. The same is true for the open-source community.
 
When supporting a range of missions, we see our responsibility as providing multiple data structures and APIs concurrently. We can group multiple data structures under one API, however until we have exercised all the missions a single API is unlikely to contain all the necessary data structures. We envisage extending the open API incrementally through each mission.
