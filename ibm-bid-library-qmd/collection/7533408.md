Reference architecture
Azure Virtual Desktop (AVD) Foundation is an IBM-Nordcloud-packaged MS Azure cloud-native reference architecture (Figure 1) for virtual desktop infrastructure (VDI) that offers a faster and more secure user experience at a lower cost. It is part of and compatible with the Azure LZ recommended by Microsoft.

Figure 1: Azure Virtual Desktop Foundation
Architectural components:
An AVD host pool is a collection of Azure VMs that register to AVD as session hosts when the AVD agent is run. All session host VMs in a host pool are sourced from the same OS image, for a consistent user experience. The 2 types of host pools are:
- Personal: Each session host is assigned to individual users.
- Pooled: Session hosts can accept connections from any user authorised to an app group within the host pool.
An application group is a logical grouping of applications installed on session hosts in the host pool. The 2 types of app groups are:
- RemoteApp: Users access the remote apps, individually selected and published to the app group.
- Desktop, where users access the full Windows desktop.
A workspace is a logical grouping of application groups in Azure Virtual Desktop. Each AVD application group must be associated with a workspace for users to see the remote apps and desktops published to them.

Connectivity and access
Network topology architecture and access will be exclusive for internal and external users, based on the best practices and delivery experience of IBM.
Internal users: Network traffic for the AVD solution for internal users leverages both private and Azure ExpressRoute peering to access the front-end and back-end VMs.
External users: Network traffic for external users will leverage the Microsoft public-facing AVD platform over the internet.
Internal and external users will be prompted for authentication against AAD and challenged for MFA, as recommended by Microsoft. AVD will use reverse connect transport to establish the remote session and carry RDP traffic.
IBM’s experiences and best practices in VDI connectivity:
- Avoid direct RDP access to session hosts in environment, as the reliance of RDP on TCP makes it vulnerable to public network latency and inconsistent packet flow.
- Determine and verify bandwidth and latency requirements using AVD Experience Estimator and Azure networking as well as network security best practices.
- Dedicated subnet(s) deployed within the target VNet to host the pool of VMs for that client.
- Achieve connectivity via direct MPLS solutions, site-to-site VPN solutions or third-party SD WAN solutions, e.g., Equinix Data Fabric.
- “RDP Shortpath” to improve end-user experience with latency-sensitive applications.
IBM's experiences and best practices in VDI access control:
- Establish tiered admin access, avoiding giving end users admin access to virtual desktops (VDs). In a multisession environment, restrict end-user software installation, operating system access, and device configuration. Limit local and remote file access permissions.
- Implement AVD security guide’s practices to protect access, identities, and session hosts.
- Set maximum inactive time, disconnection policies, and screen locks for idle sessions to preserve resources and prevent unauthorised access.
- Use AVD’s granular access control and isolated user sessions to reduce its attack surface.
- Use multifactor authentication, just-in-time (JIT) access and jump boxes to restrict access to Azure VMs and overcome malicious attacks.
- Install endpoint detection to provide advanced detection and response capabilities (e.g., MS Defender).
